    ESCENA 1 · INT. GHERKIN — DÍA

    El lenguaje del negocio

    Antes de escribir una sola línea de Java, hay que aprender a describir el comportamiento en un idioma que negocio, QA y desarrollo puedan leer sin traducir nada.

    ¿Qué es Gherkin?Primer contacto con el lenguaje, en español.
    Introducción a Gherkin (Parte 1)El camino hacia Cucumber, explicado paso a paso.
    Por qué importa: Gherkin no existe para que el código se vea bonito. Existe para que un Product Owner, un QA y un desarrollador lean el mismo archivo .feature y entiendan exactamente lo mismo.

    Estructura de un escenario

    # Ejemplo de escenario Gherkin Feature: Login de usuarios Scenario: Usuario inicia sesión correctamente Given que estoy en la página de login When ingreso mis credenciales válidas Then debo ver el dashboard principal
    Regla de oro: Given = contexto · When = acción · Then = resultado esperado.

    Scenario Outline: cuando un caso no basta

    En un proyecto real casi nunca pruebas un solo dato. Necesitas probar el mismo flujo con varios usuarios, productos o combinaciones. Para eso existe Scenario Outline + Examples: el mismo escenario se ejecuta una vez por cada fila de la tabla.

    Scenario Outline: Login con distintos roles Given que estoy en la página de login When ingreso el usuario "<usuario>" y la contraseña "<clave>" Then debo ver el rol "<rol_esperado>" Examples: | usuario | clave | rol_esperado | | admin | admin123 | Administrador | | juan | juan123 | Vendedor | | ana | ana123 | Solo lectura |
    Por qué importa: sin Scenario Outline terminas copiando y pegando el mismo escenario 5 veces con un solo dato distinto — un dolor de cabeza para mantener. Con una tabla de Examples, agregar un caso nuevo es agregar una fila, no un escenario completo.

    ESCENA 2 · INT. CUCUMBER — DÍA

    Conectando Gherkin con el código

    Cucumber es el intérprete: toma cada línea del .feature y la conecta con un método Java real llamado step definition.

    Tutorial de Cucumber con Java — Capítulo 1: Hola mundoPrimer capítulo de la serie, en español. El mismo canal continúa con capítulos 2, 3... busca su nombre exacto en YouTube para seguir la serie completa.

    Anatomía de un step definition

    @Given("que estoy en la página de login") public void estoyEnLogin() { actor.attemptsTo(Open.browserOn().the(LoginPage.class)); } @Then("debo ver el dashboard principal") public void deboVerDashboard() { assertThat(actor.asksFor(Text.of(DASHBOARD_TITLE))).isEqualTo("Dashboard"); }

    Hooks: preparar y limpiar el escenario

    Todo proyecto real necesita hacer algo antes de cada escenario (abrir el navegador, loguearse) y algo después (cerrar el navegador, limpiar datos). Para eso existen los Hooks.

    @Before public void setUp() { // se ejecuta antes de CADA escenario actor = Actor.named("Ana").whoCan(BrowseTheWeb.with(driver)); } @After public void tearDown() { // se ejecuta después de CADA escenario, incluso si falló driver.quit(); }

    Tags: eligiendo qué correr y cuándo

    No siempre quieres correr toda la suite. Antes de un despliegue urgente corres solo el humo (@smoke); en el pipeline nocturno corres todo (@regression). Los tags te dejan filtrar sin tocar código.

    @smoke @login Scenario: Login con credenciales válidas Given que estoy en la página de login ...
    En la práctica: ejecutas mvn test -Dcucumber.filter.tags="@smoke" y Cucumber corre solo los escenarios marcados, ideal para validaciones rápidas antes de un deploy.

    ESCENA 3 · INT. SCREENPLAY — NOCHE

    El patrón dorado: actores, tasks y questions

    Screenplay modela cada prueba como una obra: un actor con habilidades, que intenta tareas y luego pregunta cosas sobre el resultado.

    Curso Serenity BDD / Screenplay Web en EspañolPlaylist completa: configuración, tasks, questions y assertions con el patrón Screenplay.

    Recurso extra: si además necesitas probar APIs, busca en YouTube "Curso Serenity BDD | Screenplay Rest en Español", del mismo autor.

    Los 4 pilares de Screenplay

    ACTOR

    El protagonista

    Quien ejecuta las acciones dentro de la prueba.

    Actor.called("Juan")
    ABILITY

    La habilidad

    Lo que el actor puede hacer (navegar, llamar una API...).

    can(BrowseTheWeb.with(driver))
    TASK

    La tarea

    Lo que el actor quiere lograr, paso a paso.

    actor.attemptsTo(Login.with(user, pass))
    QUESTION

    La pregunta

    Lo que el actor quiere saber, para poder afirmarlo.

    actor.asksFor(Title.isEqualTo("Dashboard"))

    Reto: crea una task de login

    Screenplay vs. Page Object: ¿cuándo usar cada uno?

    No es que uno sea "el bueno" y otro "el viejo" — resuelven problemas distintos. Esto es lo que de verdad cambia entre los dos:

    PAGE OBJECT

    Modela una pantalla

    Una clase por página, con sus localizadores y acciones. Simple de entender, pero crece mal: si dos flujos comparten pasos, terminas duplicando código entre clases de página.

    loginPage.enterUser("ana"); loginPage.enterPass("123"); loginPage.clickLogin();
    SCREENPLAY

    Modela una intención

    Una Task describe QUÉ quiere lograr el actor, no en qué pantalla está. Se reutiliza entre features distintos y escala mejor en suites grandes, a cambio de más piezas que aprender al inicio.

    actor.attemptsTo( Login.withCredentials("ana","123") );
    Regla práctica: si tu suite es pequeña (menos de ~30 escenarios) y el equipo es junior, Page Object es más rápido de arrancar. Si el proyecto va a crecer y varios flujos comparten pasos (login, navegación, checkout), Screenplay se paga solo con el tiempo.

    Diagnóstico: por qué falla un test intermitente (flaky)

    Esto es lo que más tiempo consume en automatización real, y casi nunca se enseña. Un test "flaky" es el que a veces pasa y a veces falla, sin que cambies nada. Las 4 causas más comunes:

    CAUSA 1

    Espera insuficiente

    El elemento aún no cargó cuando el test intenta interactuar con él.

    Solución: WaitUntil, no Thread.sleep
    CAUSA 2

    Selector frágil

    Un localizador basado en texto o posición que cambia con cada release.

    Solución: usar data-testid estables
    CAUSA 3

    Datos compartidos

    Dos tests usan el mismo usuario/registro y se pisan entre sí al correr en paralelo.

    Solución: datos únicos por test
    CAUSA 4

    Orden implícito

    Un test asume que otro corrió antes y dejó cierto estado.

    Solución: cada test se auto-configura

    Integración con CI

    Un test que solo corres manualmente en tu máquina no protege al equipo. El último paso es que Serenity corra automáticamente en cada cambio de código, dentro de un pipeline (GitHub Actions, Jenkins, GitLab CI...).

    # .github/workflows/tests.yml (ejemplo simplificado) jobs: automated-tests: runs-on: ubuntu-latest steps: - run: mvn clean verify - run: mvn serenity:aggregate # genera el reporte
    Por qué importa: el reporte de Serenity generado en CI es el que ve todo el equipo — no el que corriste en tu laptop. Eso es lo que realmente vuelve la suite confiable.
